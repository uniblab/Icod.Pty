# Focused recording and replay

**Status:** proposed planning design for option 8, selected on 2026-10-06 after PR #6 merged. No feature implementation, release, or publication is implied by this document.

## Intent and boundary

A consumer of `PtySession` should be able to opt in to a portable, bounded record of the bytes delivered to its output destination and successful terminal resizes. Another consumer should be able to validate that record and replay its events in order without starting a PTY process. This first increment is a byte transcript, not a terminal screen model or a claim that the recorded child will behave identically when rerun.

The baseline is the merged PR #6 `PtySession`: one output pump writes to a caller-provided `Stream`; `Resize(PtySize)` delegates synchronously to `PtyProcess`; `Completion` and `OutputCompletion` distinguish process, drain, and output outcomes. `PtyProcess` remains the raw-stream API. Recording is disabled by default, with no new work or ownership change for old callers.

Considered approaches:

1. **Opt-in stream-backed session recorder (selected).** A supplied writable recording stream receives a versioned event file directly from the output pump and successful resize calls. A separate streaming reader validates and replays it. This has bounded library memory and uses the existing pump, but a slow recording destination can delay output; that cost is explicit.
2. **An always-on in-memory transcript.** Simple for small sessions but unbounded or silently incomplete under sustained output, and it changes default session costs.
3. **A detached observer/worker queue.** Isolates the pump from slow storage, but adds queue overflow, concurrency, ordering, and shutdown policies. Defer until a measured use case justifies it.

## Public shape to review during implementation

- Add optional `PtySessionOptions.Recording` with a `PtyRecordingOptions` value containing a writable `Stream`, `LeaveOpen` (default `true`), and a positive finite `MaxBytes` (initial default 16 MiB). Capture and validate these before launch, including stream identity against input/output. A supplied stream is transferred to session ownership only after successful startup, and never disposed on failed startup. No file path or ambient global recorder is introduced.
- Add `PtySession.RecordingCompletion`, a task returning a `PtyRecordingResult` with `Disabled`, `Complete`, `Truncated`, `Stopped`, or `Faulted` status, recorded byte/event counts, and a recording-specific error when faulted. It settles after the recorder's end/flush/disposal attempt. A disabled session has a completed `Disabled` result. Recording faults are observable here and do not replace `OutputCompletion`, `Completion`, or the cause of a process/session failure.
- Add a stream-oriented reader and event type under `Icod.Pty`: a reader accepts a readable stream and caller-selected ownership, yields one validated output/resize event at a time, and exposes the header's initial size and terminal completion marker. A convenience replay operation copies output event bytes to a supplied destination in order, returning resize events to the caller through the event reader rather than controlling a PTY or invoking arbitrary callbacks. Name and signature details are finalized against the public API baseline in RR01; the semantics here are binding.
- The recording stream contains terminal output, which may contain secrets. Recording is an explicit choice; diagnostics and errors contain structural information only. Never log payloads, input bytes, environment variables, or file contents. Input capture, matching, scripting, screen emulation, and exporters remain future portions of option 8/4/12. `PtyRecordingOptions.MaxBytes` defaults to 16 MiB. Reader limits are independent and default to 64 MiB total input and 16 KiB per output frame.

## Event and lifecycle contract

- Format version 1 uses little-endian integers. Its 16-byte header is: eight magic bytes `49 63 6f 64 50 74 79 00` (`IcodPty` plus NUL), UInt16 version `1`, UInt16 header size `16`, UInt16 initial columns, and UInt16 initial rows. Every frame starts with a 16-byte header: byte kind, three reserved zero bytes, Int64 nonnegative elapsed `TimeSpan` ticks, and UInt32 payload length. Kind 1 is output with 0–16384 payload bytes; kind 2 is resize with UInt16 columns and rows; kinds 3, 4, and 5 are zero-payload complete, truncated, and stopped terminal markers. Timestamps are nondecreasing. A file ends immediately after one terminal marker. The writer reserves its 16 bytes under `MaxBytes`; the minimum file and configured cap are 32 bytes. Version, reserved bytes, sizes, lengths, time order, missing markers, and trailing data are validated.
- Split output into frames of at most the current 16 KiB pump buffer size. Record only a chunk whose write to `PtySessionOptions.Output` returned successfully; do not claim byte-level atomicity on a destination that partially writes and then throws. An output failure is already a session output failure. Flush recording during finalization, not on every frame.
- Record a resize only after the native `Resize` call succeeds. Use a recorder-owned serialization gate shared by output and resize paths. The recorded order is the order in which completed operations enter this gate; it is not a guarantee about when the remote child observed a resize relative to bytes already in flight. Do not hold the session coordinator gate while writing caller streams. A resize that fails, an initial size only represented in the header, and input writes produce no event.
- When the cap is reached, emit one truncated terminal marker, stop recording, continue normal output/resize/session processing, and report `Truncated`. A successful end emits a complete terminal marker. Cancellation or disposal before output drains yields `Stopped` if the recorder can close the file cleanly; a sink write/flush failure yields `Faulted` and may leave an incomplete file. Recorder stream I/O is serialized; slow or noncooperative streams can delay output, synchronous resize, and finalization, as with the existing supplied output stream contract. Do not silently drop events while reporting `Complete`.
- Replay never opens a PTY, launches a child, or uses wall-clock sleeps by default. It preserves event order and payload bytes. Timestamp deltas are metadata only in this increment; timed playback is deferred. The reader enforces independent maximum frame and total-input limits, validates magic/version/kinds/sizes/lengths/nondecreasing time, rejects truncated files lacking a valid terminal marker and extra bytes after that marker, and distinguishes a valid `Truncated` recording from damaged input. It must not allocate based on untrusted lengths before checking limits.
- Reader/replay cancellation stops reads/writes and leaves caller streams open by default. Events returned by the reader own their payload memory so the next read cannot mutate earlier events. A corrupted or unsupported file produces a documented format exception, with no payload in the message. Playback of a valid truncated file replays its captured prefix and returns a truncated outcome.

## Invariants and acceptance

- Existing session callers without `Recording` retain public behavior, output ordering, ownership, cancellation, diagnostics, and error classification; `PtyProcess` and Unix helper wire protocol are unchanged.
- A successful recording round-trips embedded NUL, invalid UTF-8, empty output, multi-frame output, and resizes across all three TFMs and six platform/RID jobs. Golden files produced on one platform decode identically on the others. A replayed prefix matches the bytes actually accepted by the destination in the successful-write case.
- The cap bounds library-managed payload buffering and file bytes; repeated resizes and a high-output child cannot escape the cap. Report exact truncation and preserve the live session. Sink failure is independently observable and cannot turn a successful output write into a reported output failure. All recording results settle under normal EOF, drain timeout, cancellation, shutdown, and disposal.
- Corrupt, unsupported, oversized, incomplete, and trailing-data files fail validation without disproportionate allocations. No terminal-content data appears in lifecycle diagnostics, exception text, or CI logs.
